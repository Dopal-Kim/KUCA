# 00. 공통 — 생성형 AI로 작업하는 방법

역할별 가이드(`A_아트_출현규칙.md`, `B_앱화면.md`, `C_서버_AI.md`)를 쓰기 전에 이 문서를 먼저 읽습니다.
전체 라운드와 역할은 [`../로드맵_역할분담.md`](../로드맵_역할분담.md)에 있습니다.

## 이 가이드를 읽는 법

각 작업 카드에는 다섯 칸이 있습니다.

| 칸 | 뜻 |
| --- | --- |
| **목표 · 완료 기준** | 팀이 합의한 것. 바꾸려면 팀에 먼저 말합니다 |
| **지금 코드** | 출발점이 되는 파일. AI에게 그대로 알려 주세요 |
| **🟨 작업자가 결정할 것** | 일부러 비워 둔 칸. 작업자가 정하고 `결정:` 뒤에 적습니다 |
| **🔗 맞춰야 할 것** | 다른 사람 작업과 이어지는 약속. 정하기 전에 상대와 합의합니다 |
| **AI 진행 순서** | AI에게 시킬 순서와 예시 문장 |

결정 칸은 아래처럼 채우고 같은 PR에 넣습니다. 나중에 AI가 이 기록을 읽고 일관되게 작업합니다.

```
- 몇 개의 시간대로 나눌지
  결정: 4개 (아침/낮/저녁/밤) — 최원준, 10/10. 이유: 수업 시간표와 맞추기 쉬움
```

## 작업 한 건의 흐름

1. **카드 고르기** — 자기 역할 가이드에서 이번 라운드 카드를 고릅니다.
2. **브랜치** — 최신 main에서 `feature/<이름>-<기능>` 브랜치를 만듭니다.
3. **결정 먼저** — 🟨 칸을 AI와 상의해 정하고 문서에 적습니다. 🔗 칸은 상대에게 확인받습니다.
4. **설계 → 구현** — AI에게 바로 코드를 쓰게 하지 말고, 먼저 계획을 받고 확인한 뒤 진행합니다.
5. **확인** — 카드의 "확인 방법"을 직접 해 봅니다. Unity는 에디터 Play, 가능하면 폰.
6. **PR** — main으로 PR을 열고, 파일 주인이 다른 파일을 건드렸다면 그 사람을 리뷰어로 지정합니다.

## AI에게 줄 문장 (복사해서 쓰기)

**세션 시작**
> 이 저장소는 경희대 국제캠퍼스 산책·수집 게임 KUCA입니다 (Unity 6 URP 앱 + `server/` ASP.NET 메모 서버, Azure 배포).
> `docs/로드맵_역할분담.md`, `docs/guides/00_공통_AI작업가이드.md`, `docs/guides/<내 역할>.md` 를 먼저 읽으세요.
> 이번 작업은 카드 "<카드 번호와 이름>" 입니다. 아직 코드는 쓰지 말고, 관련 파일을 읽은 뒤
> (1) 지금 구조 요약 (2) 🟨 결정할 것마다 선택지 2~3개와 장단점 (3) 구현 계획 을 알려 주세요.

**결정 후 구현**
> 결정은 이렇게 했습니다: <결정 내용>. 가이드의 해당 🟨 칸에 기록하고, 계획대로 구현하세요.
> 내 파일 주인 범위 밖의 파일은 꼭 필요할 때만 최소로 고치고, 고친 이유를 알려 주세요.
> 끝나면 내가 직접 확인할 방법(눌러 볼 순서)을 알려 주세요.

**리뷰 받기**
> main 과 비교한 이번 브랜치 변경을 검토해 주세요. 버그, 다른 팀원 파일과 충돌할 곳, 빠진 예외 처리(네트워크 실패, 위치 권한 없음 등)를 찾아 주세요.

**막혔을 때**
> <증상>이 생깁니다. 재현 순서: <순서>. 에러 로그: <로그>. 추측으로 고치지 말고 원인부터 찾아 주세요.

## AI에게 맡길 때 지킬 것

- **한 번에 한 카드.** 여러 기능을 한 PR에 섞지 않습니다.
- **Unity 씬(`SampleScene.unity`)은 AI가 직접 고치지 않게** 합니다. 오브젝트는 코드에서 만들거나, 씬 수정이 필요하면 사람이 에디터에서 합니다.
- **`.meta` 파일**은 Unity가 만든 것을 그대로 커밋합니다. AI가 임의로 만들면 GUID가 꼬입니다.
- **API 키·비밀번호는 저장소에 넣지 않습니다.** 서버 키는 Azure 앱 설정 / 로컬은 `dotnet user-secrets`. 앱(Unity)에는 AI 키를 넣지 않고 항상 서버를 거칩니다.
- **AI가 "됐다"고 해도 직접 돌려 봅니다.** 이 프로젝트는 AI가 Unity를 실행해 볼 수 없는 환경이 많습니다.
- **기획서와 다른 판단**을 하게 되면 PR 설명에 적습니다 (발표 때 기획서와 맞춰야 하므로).

## 역할 사이 약속 (🔗 모음)

여기 있는 약속은 정해지면 이 표에 적습니다. 한쪽이 바꾸면 다른 쪽이 깨지는 것들입니다.

| 약속 | 주는 쪽 → 쓰는 쪽 | 정할 것 | 결정 |
| --- | --- | --- | --- |
| 출현 조건 데이터 | A → B (도감 "언제 나와요" 힌트) | 파일 위치·형식 | |
| 희귀 색 개체 표시 | A → B (`GameProgress.Caught` 필드) | 필드 이름·값 | |
| 좋아요·댓글 API | C → B | `docs/api.md` 에 추가 | |
| 쪽지 필터 거절 응답 | C → B | 상태 코드·사용자에게 보일 문구 | |
| 탐방 추천 API | C → B | 입력·출력 JSON | |
| 공지 API | C → B | 공지 ↔ 장소 ID 연결 형식 | |
| 날씨 정보 | C 또는 A → A | 앱에서 직접 vs 서버 경유 | |
| 퀘스트 보상 | A(액세서리) → B(지급) | 아이템 id 목록 | |

API는 항상 **`docs/api.md`를 먼저 고친 PR**로 합의하고, 그다음 서버·앱을 구현합니다.
