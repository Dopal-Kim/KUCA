### 기획서와 실제 구현이 다른 곳 (문서를 고치거나 팀이 결정)
- 기술 구성에 **Firebase**로 적혀 있지만 실제 서버는 **ASP.NET + Azure**입니다 → 기획서를 Azure로 고치는 것을 권장.
- 제외 범위에 **AR**이 있지만 AR 잡기가 이미 구현됐습니다 → 제외 범위에서 빼고 "랜덤 쿠옹이만 AR"로 정리.
- 기획서 빈칸: 근거(설문), 구조도, 팀 역량, 최소 버전 범위, 역할 분담, 일정, 참여 유도, 성공 지표, 미해결 질문.

## 5. 생성형 AI로 작업할 때 규칙

1. **각자 브랜치에서**: `feature/<이름>-<기능>` 으로 만들고 PR 로 main 에 합칩니다. main 에 바로 올리지 않습니다.
2. **시작 전에 main 받기**: 작업 시작 때마다 최신 main 을 자기 브랜치에 합칩니다.
3. **AI에게 처음 줄 말** (복사해서 쓰세요):
   > 이 저장소는 경희대 국제캠퍼스 산책·수집 게임 KUCA (Unity 6 URP + ASP.NET 메모 서버) 입니다.
   > `docs/로드맵_역할분담.md` 와 `docs/api.md` 를 먼저 읽으세요. 나는 팀원 ○ 이고 이번 작업은 "○○○" 입니다.
   > 내 파일 주인 범위 밖의 파일은 꼭 필요할 때만 최소한으로 고치고, 고친 이유를 커밋 메시지에 적어 주세요.
4. **남의 파일을 고쳐야 하면** 먼저 단톡에 알리고, 그 사람 PR 이 먼저 합쳐진 뒤에 작업합니다.
5. **API 를 바꿀 때**는 `docs/api.md` 를 먼저 고친 PR 을 B·C 가 함께 확인합니다.
6. **API 키는 저장소에 올리지 않습니다.** 서버의 AI 키는 Azure 앱 설정(환경 변수)에, 앱에는 AI 키를 넣지 않고 서버를 거쳐 부릅니다.
7. **Unity 씬 파일(`SampleScene.unity`)** 은 한 번에 한 사람만 고칩니다. 가능하면 코드에서 오브젝트를 만들어 씬 수정을 줄입니다.
